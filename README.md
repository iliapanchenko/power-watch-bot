# Power Watch Bot

Телеграм-бот, який стежить за адресами в інтернеті та пише в чат, коли зв'язок із точкою зникає («світло зникло») і коли повертається («світло з'явилось», із тривалістю відключення). О 23:59 за Києвом надсилає підсумок дня.

Розрахований на кількох людей: кожен заходить за кодом-запрошенням і налаштовує свої адреси сам, у своєму чаті. Розгортається на Vercel, стан тримає в Upstash Redis, перевірку тригерить зовнішній cron. Залежностей у `package.json` немає жодної.

```
[cron-job.org]  --щохвилини-->  GET /api/check
                                     |
                                     |  4 проходи з паузою 15 с усередині виклику
                                     |-- TCP-конект --> адреси всіх чатів
                                     |
                              [Upstash Redis]  <- хто підписаний, за чим стежить,
                                     |            який статус зараз
                                     v
                              Telegram: 🔴 Квартира — світло зникло

[Telegram]      --вебхук---->  POST /api/telegram   (/add, /status, /today, ...)
```

---

## Спершу прочитай це

**Потрібна адреса, доступна з інтернету.** Vercel — це чужа хмара, вона фізично не бачить домашню `192.168.1.1`. Працює:

- білий (публічний) IP від провайдера — статичний або через DDNS-ім'я типу `myhome.ddns.net`;
- будь-який пристрій із прокинутим портом: роутер із веб-мордою на WAN, камера, NAS, сервер.

Не працює: приватні адреси і провайдери з CGNAT — там роутера з інтернету просто не існує. Бот перевіряє це при додаванні: резолвить ім'я і, якщо воно веде в приватний діапазон, відмовляє одразу з поясненням, замість того щоб потім вічно показувати «світла нема».

**ICMP-пінга тут немає.** У serverless-функціях raw-сокети заборонені, тому замість `ping` бот робить TCP-конект у порт. Практично різниці мало, з одним приємним бонусом: `ECONNREFUSED` (порт закритий, але хтось відповів) теж рахується як «живий» — тобто роутер не зобов'язаний нічого відкривати назовні, достатньо щоб він відповідав RST замість тиші. Якщо роутер мовчить у всі порти, вкажи порт прокинутого пристрою.

**Бот бачить зв'язок, а не електрику.** Обрив у провайдера при цілому світлі виглядає точно так само, як відключення. Хибних тривог тим менше, чим стабільніший інтернет на точці.

## Розгортання

### 1. Створи бота

У Telegram напиши [@BotFather](https://t.me/BotFather) → `/newbot` → збережи токен.

### 2. Заведи сховище

У проєкті на Vercel: **Storage → Create Database → Upstash (Redis)**. Vercel сам додасть `KV_REST_API_URL` і `KV_REST_API_TOKEN` у змінні оточення — код розуміє і їх, і рідні `UPSTASH_REDIS_REST_*`.

Redis тут не через швидкість, а через спосіб тарифікації: платимо за кількість команд, а не за час роботи. Postgres на цьому навантаженні не встигав би засинати й проїдав би безкоштовний ліміт компʼюта до середини місяця. Деталі — у розділі «Скільки це коштує».

### 3. Залий код

```bash
git push
```

Далі на Vercel: **Add New → Project → Import** свій репозиторій. Фреймворк — **Other**, білдити нічого не треба.

### 4. Пропиши змінні оточення

Vercel → Settings → Environment Variables:

| Змінна | Значення |
|---|---|
| `BOT_TOKEN` | токен від BotFather |
| `KV_REST_API_URL`, `KV_REST_API_TOKEN` | з'являться самі, якщо Upstash підключено через Vercel |
| `CRON_SECRET` | довгий випадковий рядок, напр. `openssl rand -hex 24` |
| `INVITE_CODE` | код, який роздаєш родичам. **Порожній = бот відкритий для всіх** |
| `ADMIN_IDS` | твій Telegram id: код не потрібен, доступна команда `/admin` |
| `MAX_DEVICES_PER_CHAT` | (необов'язково) ліміт адрес на людину, типово `3` |
| `MAX_CHATS` | (необов'язково) скільки чатів пускати всього, типово `25` |
| `DEFAULT_MODE` / `DEFAULT_TEMPO` | (необов'язково) типові пресети, типово `звичайний` |
| `PROBE_TIMEOUT` | (необов'язково) таймаут конекту в мс, типово `4000` |
| `MAX_RUN_SECONDS` | (необов'язково) скільки живе один виклик `/api/check`, типово `55` |
| `SUMMARY_HOUR` / `SUMMARY_MINUTE` | (необов'язково) коли підбивати добу, типово `23` / `59` |

`CRON_SECRET` працює одразу як пароль до `/api/check` і як підпис вебхука від Telegram — стороння людина, яка вгадала URL, нічого зробити не зможе.

Після додавання змінних зроби **Redeploy**.

### 5. Ініціалізуй

Відкрий у браузері один раз:

```
https://<твій-проєкт>.vercel.app/api/setup?key=<CRON_SECRET>
```

**Це єдиний крок, який не робиться сам при деплої.** Разом із вебхуком реєструється список типів оновлень (`allowed_updates`), і зберігається він на боці Telegram, а не в коді. Усе, чого немає в списку — дописи каналів, натискання кнопок — Telegram мовчки відкидає: без помилки, без логів, без натяку. Тому після кожного оновлення коду сюди варто зайти ще раз, а після появи нового типу оновлень — обов'язково. Перевірити, що саме зараз діє, можна через `getWebhookInfo` у Bot API.

Ручка реєструє вебхук, меню команд і перевіряє, що Redis відповідає. У відповіді подивись на поле `inviteCode` — якщо там `ВИМКНЕНО`, бот пускає будь-кого. Смикати цю ручку можна скільки завгодно разів; після оновлення коду зайди сюди ще раз.

### 6. Постав cron

На [cron-job.org](https://cron-job.org) створи задачу:

- **URL:** `https://<твій-проєкт>.vercel.app/api/check`
- **Schedule:** every 1 minute
- **Headers:** `Authorization: Bearer <CRON_SECRET>`

Щохвилини — це частота запусків, а не перевірок. Всередині одного виклику бот робить чотири проходи з паузою `SWEEP_INTERVAL`.

Таймаут у планувальнику можна лишити типовим: `/api/check` відповідає одразу, за частки секунди, а проходи доганяє у фоні через `waitUntil`. Виклик живе 55 секунд, і якби він тримав з'єднання відкритим, планувальник із таймаутом 30 секунд рахував би кожен запуск як провалений — і зрештою вимкнув би задачу за «надто багато помилок».

Побачити, що саме напрацював прохід, можна руками: `/api/check?key=...&once=1` виконується синхронно й віддає повний JSON.

### 7. Заходь

Напиши боту `/start <код>`, потім додай адресу:

```
/add myhome.ddns.net Квартира
/add 178.12.34.56:80 Дача
```

Родичам даєш посилання на бота і той самий код.

## Команди

| Команда | Що робить |
|---|---|
| `/start <код>` | зайти за запрошенням |
| `/status` | що зі світлом просто зараз і скільки вже так |
| `/today` | скільки світла не було сьогодні |
| `/check` | разова проба негайно, без очікування |
| `/list` | адреси з деталями: хост, порт, остання перевірка, затримка |
| `/add адреса Назва` | додати адресу (порт типово 443) |
| `/rm номер` | прибрати адресу, номер з `/list` |
| `/mode` | чутливість до коротких провалів, своя в кожного чату |
| `/settings` | поточні налаштування простою мовою |
| `/tempo` | крок опитування, спільний для всіх; лише для `ADMIN_IDS` |
| `/stop` | відписатись і видалити свої дані |
| `/id` | показати свій Telegram id |
| `/admin` | тільки для `ADMIN_IDS`: скільки чатів і адрес усього |

`/mode` і `/tempo` показують екран із кнопками — обирати можна натисканням, без набирання команд. Текстова форма (`/mode спокійний`, `/mode 3`) теж працює.

Кнопку під дописом у каналі бачить кожен підписник, тому перед зміною бот питає в Telegram, ким ця людина є в цьому чаті: чутливість міняють лише адміністратори, а темп — лише `ADMIN_IDS`. Стороннє натискання отримує спливне пояснення, і нічого не змінюється.

Працює і в групі, і в каналі: додай бота (у канал — адміністратором із правом публікувати) і напиши `/start <код>` там.

## Як приймається рішення

Статус міняється не з першої тиші, а за гістерезисом: кілька провалів поспіль → «світло зникло», кілька відповідей поспіль → «світло з'явилось». Без цього один загублений пакет о третій ночі будив би двома повідомленнями поспіль.

Скільки саме — вирішують два пресети.

**`/mode` — чутливість, своя в кожного чату.** Комусь потрібне сповіщення за пів хвилини, а комусь важливіше не отримувати його щоразу, як розетка моргне Wi-Fi.

| Пресет | Провалів | Тиша до сповіщення |
|---|---|---|
| `швидкий` | 2 | ~30 с |
| `звичайний` | 4 | ~60 с |
| `спокійний` | 8 | ~2 хв |

**`/tempo` — крок опитування, спільний для всіх.** Він визначає, скільки конектів на хвилину бот робить із інфраструктури Vercel, тому доступний лише власнику.

| Пресет | Крок | Проб на хвилину з адреси |
|---|---|---|
| `частий` | 10 с | 6 |
| `звичайний` | 15 с | 4 |
| `економний` | 30 с | 2 |

Реакція чату = крок × поріг. `/settings` рахує це й показує звичайною мовою.

Вільного вводу чисел свідомо немає. Усі три темпи ділять 60 націло — інакше на стику хвилин утворився б розрив, довший за сам крок, і обіцяна реакція виявилась би брехнею. Це перевіряється тестом.

Повернення світла в усіх режимах фіксується однаково швидко: притримувати хороші новини сенсу немає.

Триваюче відключення ріжеться по межі доби: якщо світла нема з 22:00 до 03:00, у вчорашній підсумок піде дві години, у сьогоднішній — три. Інакше довгі нічні відключення не потрапляли б у жоден звіт.

## Про частоту перевірок

Жоден зовнішній планувальник не вміє інтервалу меншого за хвилину: ні cron-job.org, ні UptimeRobot, ні Vercel Cron. Тому частоту задає не cron, а сам `/api/check`: він робить проходи по сітці `0, 15, 30, 45` секунд від свого старту і завершується до того, як прийде наступний виклик. Виходить рівний крок у 15 секунд без розривів на межі хвилини.

Два запобіжники:

- **Замок у Redis.** Якщо попередній виклик ще не завершився, наступний одразу виходить із `{"skipped":"already running"}`. Інакше адреси перевірялись би вдвічі частіше, а про одну зміну статусу прилетіло б два повідомлення.
- **`MAX_RUN_SECONDS` (55) менший за `maxDuration` (60) у `vercel.json`.** Функція встигає вийти сама, а не гине посеред проходу. Якщо міняєш одне, міняй і друге.

## Скільки це коштує

**Redis.** Увесь стан читається один раз на виклик функції, а не на кожен прохід, і пишеться назад теж один раз — плюс позачерговий запис одразу після сповіщення, щоб при падінні функції те саме не надіслалось удруге. Виходить близько 6 команд на хвилину, тобто ~260 тис. на місяць проти 500 тис. безкоштовних. Кількість людей на це майже не впливає: всі чати читаються одним `MGET`.

**Vercel.** Функція зайнята майже безперервно — ~55 секунд щохвилини. На Hobby-тарифі це відчутна частка безкоштовного ліміту, тому подивись **Vercel → Usage** за перші пару днів. Якщо піджимає:

| Що зробити | Реакція | Завантаження функції |
|---|---|---|
| `SWEEP_INTERVAL=15` (типово) | ~30 с | ~55 с щохвилини |
| `MAX_RUN_SECONDS=20` | ~30 с, але з провалом на 40 с наприкінці кожної хвилини | ~20 с щохвилини |
| `?once=1` в URL cron-задачі | ~2 хв | частки секунди |

## Про відкритий доступ

Кожна адреса — це TCP-конект з інфраструктури Vercel чотири рази на хвилину. Якщо прибрати `INVITE_CODE`, бот стає безкоштовним сервісом, який довбиться в будь-яку адресу на замовлення незнайомців; питання виникнуть не до них, а до твого акаунта. Тому:

- `INVITE_CODE` заповнений — типовий і рекомендований режим;
- `MAX_DEVICES_PER_CHAT` і `MAX_CHATS` тримають стелю навантаження;
- приватні, службові та CGNAT-діапазони відхиляються при додаванні — і щоб людина не чекала сповіщень від недосяжної адреси, і щоб через бота не можна було мацати внутрішню мережу.

## Локальна перевірка

Чи взагалі відповідає адреса, перш ніж її додавати:

```bash
node scripts/probe-test.mjs myhome.ddns.net 443
node scripts/probe-test.mjs            # вбудовані приклади
```

Логіка станів на вигаданому годиннику — гістерезис, тривалості, межа доби:

```bash
node scripts/status-test.mjs
```

Розкладка проходів усередині виклику:

```bash
node scripts/sweep-test.mjs
```

Пресети й те, як кожен темп лягає на хвилинну сітку:

```bash
node scripts/presets-test.mjs
```

Тексти екранів налаштувань, із підробленим Redis у пам'яті:

```bash
node scripts/preview-commands.mjs
```

Запуск усього проєкту локально:

```bash
npm i -g vercel
cp .env.example .env    # заповни
vercel dev
```

## Якщо щось не так

**Бот мовчить на команди.** Перевір, чи `/api/setup` відпрацював, і подивись `https://api.telegram.org/bot<TOKEN>/getWebhookInfo` — там буде `last_error_message`.

**Адреса завжди 🔴, хоча світло є.** Найчастіше вона недосяжна ззовні: CGNAT, або роутер дропає все на WAN. Перевір `scripts/probe-test.mjs` із чужої мережі (мобільний інтернет, не свій Wi-Fi). Спробуй порт реально прокинутого пристрою.

**Статуси стрибають.** Підніми `FAIL_THRESHOLD` до 3-4 або `PROBE_TIMEOUT` до 8000 — при поганому каналі конект не встигає за 4 секунди.

**Тиша від cron.** Смикни `/api/check?key=...&once=1` руками — має прийти JSON із кількістю чатів і адрес.

**`/api/check` завжди відповідає `{"skipped":"already running"}`.** Замок залишився від виклику, який упав, не встигнувши звільнити його. Сам розсмокчеться через `MAX_RUN_SECONDS`; якщо ні — подивись логи функції у Vercel.

**Динамічний IP змінився.** Тому й краще DDNS-ім'я замість голого IP — інакше після переобрання адреси бот стежитиме за чужим підключенням.
